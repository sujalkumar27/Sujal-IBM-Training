01 ORM Concepts & the Java Persistence API (JPA)

Skip the boilerplate SQL — let Java objects talk to the database directly.

What A layer that maps Java classes to database tables.
Why Writing SQL for every save/load is repetitive and error-prone.
How Annotate classes; the ORM generates the SQL.

The core idea

In Java, you think in objects: a User object with name and email fields. In a database, the same information lives in a row of a users table. Object-Relational Mapping (ORM) is a middle layer that automatically translates between these two worlds:

  • Java class ↔ database table
  • Java field ↔ table column
  • Java object instance ↔ table row
  • Java reference to another object ↔ foreign key

What is JPA specifically?

JPA (Java Persistence API) is not a library — it is a specification. It defines a standard set of interfaces (EntityManager, Query), annotations (@Entity, @Id, @OneToMany), and rules for how ORM should behave in Java. To actually run JPA code you need an implementation:

  • Hibernate — the most popular, feature-rich implementation.
  • EclipseLink — the reference implementation.
  • OpenJPA — Apache's implementation.

Think of JPA as "the USB standard" and Hibernate as "one specific USB cable."

Why not just write SQL?

  • Less code — no manual row-to-object conversion (ResultSet.getString(...) everywhere).
  • Portable — same code runs on MySQL, Postgres, Oracle. The ORM translates SQL dialects.
  • Type-safe — the compiler catches typos in field names.
  • Caching — ORM caches results, reducing DB calls.
  • Relationships handled automatically — call user.getOrders(), ORM runs the join.

Minimal example

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String name;

    @Column(unique = true)
    private String email;

    // getters, setters, constructors...
}

// Saving is one line
entityManager.persist(new User("Sujal", "sujal@example.com"));
Real-World Use Case — E-commerce app An online store has Customer, Product, Order, and OrderItem classes. Instead of writing hundreds of SQL statements to insert orders, fetch customer histories, and update inventory, the team uses JPA. The result: 80% less database code, and switching from MySQL to PostgreSQL later took only a config change.
Trade-off ORM can hide performance issues (see N+1 problem, section 7). Complex reporting queries are still often clearer in raw SQL.

Why Battle-tested, huge community, works with Spring.

Real-World Use Case — Banking system A bank's core account service uses Hibernate. When a customer transfers money, Hibernate opens a Session, loads both accounts (managed state), the code mutates balances, and on commit Hibernate generates two UPDATE statements plus an INSERT for the audit log — all inside one transaction. If any step fails, everything rolls back.
Why Hibernate beats plain JDBC
  • Dirty checking — no manual UPDATE calls.
  • Automatic connection pooling.
  • Caching (L1 by default, L2 optional).
  • Lazy loading of related data.

03 Entity Mapping and Relationships (1:1, 1:N, N:M)

Model how tables connect — the way the real world does.

What Annotations that describe joins between tables.
Why Real data is connected: users have orders, orders have items.
How @OneToOne, @OneToMany, @ManyToOne, @ManyToMany.

Three relationship types

TypeExampleForeign Key Lives On
@OneToOneUser ↔ UserProfileEither side (or a shared PK)
@OneToMany / @ManyToOneDepartment → EmployeesThe "many" side
@ManyToManyStudent ↔ CourseA separate join table

@OneToOne example — Employee & Passport

@Entity
public class Employee {
    @Id private Long id;
    private String name;

    @OneToOne(cascade = CascadeType.ALL)
    @JoinColumn(name = "passport_id")
    private Passport passport;
}

@OneToMany + @ManyToOne — the most common

@Entity
public class Department {
    @Id private Long id;
    private String name;

    @OneToMany(mappedBy = "department", cascade = CascadeType.ALL)
    private List<Employee> employees = new ArrayList<>();
}

@Entity
public class Employee {
    @Id private Long id;
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")   // foreign key column
    private Department department;
}

"mappedBy" tells Hibernate: "I'm not the owner of this relationship — look at the other side for the foreign key." The side with @JoinColumn is the owning side.

@ManyToMany with a join table

@Entity
public class Student {
    @Id private Long id;

    @ManyToMany
    @JoinTable(
      name = "student_course",
      joinColumns = @JoinColumn(name = "student_id"),
      inverseJoinColumns = @JoinColumn(name = "course_id"))
    private Set<Course> courses = new HashSet<>();
}

Cascade types — what happens to children

  • CascadeType.PERSIST — save parent → save children too.
  • CascadeType.MERGE — update parent → update children.
  • CascadeType.REMOVE — delete parent → delete children (dangerous with big trees).
  • CascadeType.ALL — everything.
Real-World Use Case — LMS (Learning Management System) Coursera-style apps use all three relationships: a User has one Profile (1:1); a Course has many Lessons (1:N); Students enroll in many Courses and each course has many students (N:M through an "enrollment" join table that also stores enrollment date and grade).
Common mistake Using List instead of Set for @ManyToMany — this causes Hibernate to fire many extra queries. Use Set for many-to-many, or promote the join to a real entity if you need extra fields.

04 JPQL, Criteria API and Native Queries

Three ways to ask the database for exactly what you want.

What Query mechanisms provided by JPA.
Why Finder methods aren't enough for complex reads.
How Pick one based on how dynamic and portable it needs to be.

JPQL — Java Persistence Query Language

Looks like SQL but works on entity classes and fields, not tables and columns. Portable across databases.

// JPQL — 'User' is the entity, 'name' is the Java field
String jpql = "SELECT u FROM User u WHERE u.age > :minAge ORDER BY u.name";
TypedQuery<User> query = em.createQuery(jpql, User.class);
query.setParameter("minAge", 18);
List<User> users = query.getResultList();

Criteria API — build queries in code

Everything is Java objects — no strings. Verbose, but perfect when the query is built dynamically.

CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<User> cq = cb.createQuery(User.class);
Root<User> root = cq.from(User.class);

List<Predicate> where = new ArrayList<>();
if (nameFilter != null) where.add(cb.like(root.get("name"), "%" + nameFilter + "%"));
if (minAge != null)     where.add(cb.gt(root.get("age"), minAge));

cq.where(cb.and(where.toArray(new Predicate[0])));
List<User> result = em.createQuery(cq).getResultList();

Native SQL — full power, less portable

When you need database-specific features (window functions, JSON operators, hierarchical queries).

Query q = em.createNativeQuery(
    "SELECT * FROM users WHERE created_at > NOW() - INTERVAL '30 days'",
    User.class);
List<User> recent = q.getResultList();

Which one, when?

SituationBest Choice
Simple static queryJPQL (or Spring Data derived query)
Filters chosen by user at runtimeCriteria API
Vendor feature (JSONB, CTE, PIVOT)Native SQL
Reporting with joins across many tablesNative SQL — clearer & faster
Real-World Use Case — Airbnb-style search A listing search page has filters for price, location, dates, guest count, amenities — most optional. The team uses the Criteria API to build the query only from filters the user actually chose. A separate "recommendations" page uses a native PostgreSQL query with a window function to rank listings.

05 Spring Data JPA Repositories

Zero implementation code — Spring writes the repository for you.

What An interface layer that generates CRUD implementations at startup.
Why 90% of DAO code is boilerplate — eliminate it.
How Extend JpaRepository; name your methods correctly.

The magic of the interface

public interface UserRepository extends JpaRepository<User, Long> {

    // Derived — Spring parses the name and generates SQL automatically
    List<User> findByLastName(String lastName);
    List<User> findByAgeGreaterThanEqualAndActiveTrue(int age);
    Optional<User> findByEmail(String email);
    long countByCountry(String country);

    // Paging & sorting
    Page<User> findByCountry(String country, Pageable pageable);

    // Custom JPQL when a derived name would be ugly
    @Query("SELECT u FROM User u WHERE SIZE(u.orders) > :n")
    List<User> findUsersWithMoreThanNOrders(@Param("n") int n);

    // Native query
    @Query(value = "SELECT * FROM users WHERE created_at > ?1", nativeQuery = true)
    List<User> findRecent(LocalDate date);

    // Modifying query
    @Modifying
    @Query("UPDATE User u SET u.active = false WHERE u.lastLogin < :cutoff")
    int deactivateInactive(@Param("cutoff") LocalDate cutoff);
}

You get for free

  • save(entity), saveAll(list)
  • findById, findAll, existsById, count
  • deleteById, deleteAll
  • Paging: findAll(PageRequest.of(0, 20))
Real-World Use Case — SaaS admin panel An HR SaaS product has 40+ entity types (Employee, Payslip, Leave, Department, …). Instead of 40 DAO classes with hundreds of methods, they have 40 repository interfaces — most with only a handful of custom queries. Development on new modules is ~3× faster.
Pro tip Combine derived queries for common cases and @Query for anything complex. Don't be afraid to add a Specification or QueryDSL layer when queries get truly dynamic.

06 Transactions and the Persistence Context

The safety net that keeps your data consistent.

What A transaction groups DB ops; the persistence context tracks entities during it.
Why Partial updates corrupt data. All-or-nothing is the only safe option.
How Wrap methods in @Transactional.

ACID — the four transaction guarantees

  • Atomicity — all steps happen, or none do.
  • Consistency — DB moves from one valid state to another.
  • Isolation — concurrent transactions don't corrupt each other.
  • Durability — once committed, changes survive crashes.

@Transactional in Spring

@Service
public class TransferService {

    @Transactional  // starts + commits (or rolls back) automatically
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepo.findById(fromId).orElseThrow();
        Account to   = accountRepo.findById(toId).orElseThrow();

        from.debit(amount);
        to.credit(amount);
        // No repo.save() needed — dirty checking handles it!
        auditRepo.save(new AuditLog(fromId, toId, amount));
        // If ANY line throws, ALL previous DB changes roll back.
    }
}

Isolation levels — from loose to strict

LevelAllowsUse for
READ_UNCOMMITTEDDirty readsAlmost never
READ_COMMITTED (default in most DBs)Non-repeatable reads, phantomsGeneral web apps
REPEATABLE_READPhantoms onlyReports needing consistent snapshots
SERIALIZABLENothingFinancial calcs, strict correctness

The Persistence Context — Hibernate's magic sauce

During a transaction, Hibernate maintains an in-memory map of every entity you've touched. It gives you three big wins:

  • Identity guarantee — call findById(1L) twice and you get the same object reference.
  • Dirty checking — Hibernate compares entities at commit against their loaded state and only UPDATEs changed fields. You never call save() for updates.
  • First-level cache — repeat lookups don't hit the DB.
@Transactional
public void bumpAge(Long userId) {
    User u = userRepo.findById(userId).orElseThrow();
    u.setAge(u.getAge() + 1);        // just mutate the object
    // no save() call — Hibernate detects change and issues UPDATE on commit
}
Real-World Use Case — Payment gateway Stripe-like services wrap "charge card → record payment → send email → update ledger" in a single transaction. If the ledger update fails after the card charge, the transaction rolls back the DB changes and the code triggers a refund — the customer never sees an inconsistent state.
Gotcha — @Transactional only works on public methods called from OUTSIDE the class. Spring uses proxies, so internal self-calls bypass the transaction annotation entirely.

07 Lazy vs. Eager Loading & the N+1 Problem

The single most common Hibernate performance killer — and how to avoid it.

What Strategy for loading related entities.
Why Loading everything upfront wastes DB calls and memory; loading too late causes N+1.
How Default to LAZY, use fetch joins where needed.

Eager loading

Related data is loaded immediately with the parent, in the same query (or a follow-up).

@ManyToOne(fetch = FetchType.EAGER)   // default for @ManyToOne
private Department department;

Lazy loading

Related data is loaded only when accessed. Hibernate returns a proxy instead of the real object.

@OneToMany(fetch = FetchType.LAZY)    // default for @OneToMany
private List<Employee> employees;

Default fetch types (memorize these)

AnnotationDefault
@OneToOneEAGER
@ManyToOneEAGER
@OneToManyLAZY
@ManyToManyLAZY

The N+1 problem — the classic trap

You fetch a list of parents, then loop and access a lazy child collection. Hibernate issues 1 query for the parents, then N more — one per parent — for the children.

List<Department> depts = departmentRepo.findAll();  // 1 query
for (Department d : depts) {
    System.out.println(d.getEmployees().size());     // 1 query PER department!
}
// 10 departments = 11 queries. 1000 departments = 1001 queries.
How to spot it Enable spring.jpa.show-sql=true. If you see a burst of similar SELECT statements after opening one endpoint — that's N+1.

Fix 1 — JOIN FETCH in JPQL

@Query("SELECT DISTINCT d FROM Department d JOIN FETCH d.employees")
List<Department> findAllWithEmployees();
// Now: 1 query returns everything.

Fix 2 — @EntityGraph (declarative)

@EntityGraph(attributePaths = {"employees"})
List<Department> findAll();

Fix 3 — batch fetching

@BatchSize(size = 20)
@OneToMany(mappedBy = "department")
private List<Employee> employees;
// Instead of N queries: N/20 queries.
Real-World Use Case — Social media feed A social app loads 20 posts for the home feed. Each post has an author, likes count, and top 3 comments. Naive code triggers 20 × 3 = 60+ extra queries per page load. After adding JOIN FETCH for author and comments, page load time drops from 2.3s to 180ms.
Rule of thumb Always use FetchType.LAZY everywhere, then explicitly fetch what you need per query using JOIN FETCH or @EntityGraph. Never trust default EAGER.

08 Introduction to Database Schema Versioning

Treat your database schema like source code — versioned, reviewed, reproducible.

What Every schema change is a file, checked into Git, applied in order.
Why Manual SQL on servers = drift, mystery bugs, disaster.
How Use tools like Flyway or Liquibase.

The problem it solves

Without versioning, DB changes look like this:

  • Developer A runs an ALTER TABLE on their laptop — forgets to tell anyone.
  • Developer B pulls their code, tests fail on missing column, wastes 2 hours.
  • The change goes to staging via a Slack message: "hey run this SQL real quick."
  • Someone forgets to run it in production — deploy breaks at 2 AM.

With versioning

  • Every change is a file in the repo: V12__add_customer_status_column.sql
  • The tool tracks which migrations have run in a special table.
  • Running flyway migrate (or letting Spring Boot auto-run) applies only new files, in order.
  • Every environment ends up with the exact same schema.

Two dominant tools

FeatureFlywayLiquibase
Migration formatPlain SQLXML, YAML, JSON, or SQL
RollbackPaid featureFree, built-in
Learning curveVery easySteeper
Best forSimple, SQL-first teamsMulti-DB, complex environments
Real-World Use Case — Fintech startup A 30-engineer fintech pushes code 10+ times a day. Every migration is a numbered SQL file reviewed in a PR. When onboarding a new developer, they run docker-compose up and Flyway applies 187 migrations to bring the empty DB to the exact production state — in under 3 minutes.
Core principle Migrations are append-only. Once V5 has run in any environment, you never edit V5 — you write V6 to correct it.

09 Flyway: Versioned and Repeatable Migrations

SQL files, numbered, applied in order — that's it.

What A tool that runs SQL files in a defined order and tracks what's done.
Why Simple, predictable, no XML fluff.
How Put files in src/main/resources/db/migration/.

File naming — the golden rule

  • V1__create_users_table.sql — Versioned. Runs once, in order.
  • V2__add_email_column.sql
  • V2.1__add_email_index.sql — Dotted versions allowed.
  • R__refresh_user_view.sql — Repeatable. Runs whenever its file checksum changes.
  • U1__undo_create_users.sql — Undo (paid Teams edition).

Format: <prefix><version>__<description>.sql — note the double underscore.

What happens on startup

  1. Flyway connects to the DB.
  2. It checks flyway_schema_history table for what's already applied.
  3. It compares to the files it finds.
  4. It applies missing files in version order, each in its own transaction.
  5. It records success/failure with a checksum of the file's content.

Example migration file — V3__add_orders_table.sql

CREATE TABLE orders (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT NOT NULL REFERENCES users(id),
    total        NUMERIC(10, 2) NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_orders_user_id ON orders(user_id);

Spring Boot config

spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
spring.flyway.baseline-on-migrate=true    # for pre-existing DBs

The schema history table

Flyway creates and reads a table like this:

versiondescriptionchecksuminstalled_onsuccess
1create users-18392842026-01-15 09:12true
2add email column20194852026-01-16 14:33true
Never edit a migration that already ran anywhere. Its checksum will change, Flyway will refuse to start, and someone has to manually run flyway repair at 3 AM.
Real-World Use Case — Multi-region SaaS A SaaS deploys the same Spring Boot service to 4 regions (US, EU, APAC, LATAM), each with its own PostgreSQL. On every deployment, Flyway ensures the schema in every region matches — no more "US has column X but EU doesn't" incidents.

10 Liquibase: Changelogs and Changesets

More power, more portable, and rollback comes free.

What A DB migration tool built around XML/YAML/JSON changelogs.
Why Works across DB vendors; declarative rollbacks; contexts/labels.
How Write changelog files; run liquibase update.

Vocabulary

  • Changelog — the master file (or the root of a chain). Contains a list of changesets.
  • Changeset — a single atomic change, uniquely identified by id + author + filename.
  • Change type — the actual operation: createTable, addColumn, createIndex, etc.

YAML example

databaseChangeLog:
  - changeSet:
      id: 001
      author: sujal
      changes:
        - createTable:
            tableName: users
            columns:
              - column: {name: id, type: bigint, autoIncrement: true, constraints: {primaryKey: true}}
              - column: {name: email, type: varchar(255), constraints: {nullable: false, unique: true}}
              - column: {name: created_at, type: timestamp, defaultValueComputed: CURRENT_TIMESTAMP}
      rollback:
        - dropTable:
            tableName: users

  - changeSet:
      id: 002
      author: sujal
      changes:
        - addColumn:
            tableName: users
            columns:
              - column: {name: last_login, type: timestamp}

Why the extra structure pays off

  • Database-agnostic — bigint becomes BIGINT on Postgres, NUMBER(19) on Oracle.
  • Rollback built in — most change types auto-generate the reverse; you can also supply explicit rollback SQL.
  • Contexts — tag a changeset with context: test so seed data runs only in test environments.
  • Preconditions — skip a changeset if a table already exists.

Tracking table

Liquibase uses DATABASECHANGELOG to remember which changesets have run.

Handy commands

liquibase update                       # apply pending changesets
liquibase rollbackCount 3              # undo last 3 changesets
liquibase rollbackToDate 2026-06-01    # revert to a point in time
liquibase status                       # what's pending
liquibase diff                         # compare two DBs
Real-World Use Case — Enterprise with mixed DBs A large enterprise runs the same product on Oracle (legacy customers), PostgreSQL (new customers), and SQL Server (a regulated customer). Liquibase changelogs work across all three — the same changeset creates the right column type for each DB.

11 Managing Migrations Across Environments

Same migrations, dev → staging → prod, no manual intervention.

The 4-environment pipeline

EnvPurposeWhen migrations run
LocalDeveloper laptopApp startup or manual
Dev / IntegrationShared team DBOn every merge to main
StagingProd-like cloneOn release-candidate build
ProductionLive customersRight before app deployment

Best practices

  • Same file everywhere — never rewrite between environments. The V5 that ran in dev is the exact V5 that runs in prod.
  • Run migrations from CI/CD, not from a developer's laptop.
  • Test each migration against a prod-sized dataset in staging before prod.
  • Always take a DB backup right before running prod migrations.
  • Use contexts/profiles for env-specific data: dev/test seed data lives in context: test; it never runs in prod.
  • Baseline existing prod databases — set baseline-on-migrate=true once so Flyway/Liquibase knows the current state is the starting point.

Order of operations in a deployment

  1. Build the app image.
  2. Backup production DB.
  3. Run migrations (safe, non-breaking ones only — see topic 13).
  4. Roll out new app pods gradually.
  5. Verify health checks.
  6. If needed, run any "cleanup" migrations after the app is stable.
Real-World Use Case — GitHub Actions pipeline On merge to main: GitHub Actions spins up a Postgres container, restores a sanitized prod snapshot, runs all Flyway migrations, then runs the full integration test suite. Only if this passes does the same set of migrations reach production the next day.
Golden rule The migration file that reached production was reviewed in a pull request, applied in dev, tested in staging, and applied to prod — in that exact order, without edits.

12 Rolling Back and Handling Failed Migrations

"Undo" for databases is trickier than you think.

Two philosophies

StrategyWhat you doTrade-off
RollbackRun the reverse migration to undo the changeCan't recover dropped columns/rows — data loss
Fix-forwardWrite a new migration to correct the problemEverything stays in git history, always safe
Most teams prefer fix-forward in production. A rolled-back migration in Liquibase doesn't bring back the data you deleted; a new "fix" migration does not pretend the past didn't happen.

Rollback options

  • Liquibase: liquibase rollbackCount 1, rollbackToTag, or rollbackToDate. Free.
  • Flyway: Undo migrations in Teams (paid) edition; otherwise a manual "V+1" fix.
  • Full DB restore from backup: last resort, causes downtime.

When a migration fails partway

  • PostgreSQL: DDL is transactional; a failure auto-rolls back everything in that migration.
  • MySQL < 8.0: DDL is not transactional. Half your CREATE INDEX might have run before the failure — you'll need to inspect and clean up.
  • Flyway repair: flyway repair fixes the history table when a failed migration blocks further attempts.
  • Fix the underlying SQL, re-run.

Rollback-safe migrations — a checklist

  • Never drop a column in the same release the app stops writing to it.
  • Never rename a table in a single step.
  • Prefer ALTER TABLE ADD (safe) over ALTER TABLE DROP (destructive).
  • Split risky changes into expand → migrate → contract (next topic).
Real-World Use Case — Startup crisis avoided A team deploys a "cleanup" migration that drops an "unused" column — turns out a legacy reporting job still needed it. Instead of rolling back (which wouldn't restore the data anyway), they restore the column from last night's backup with a new V-migration, then write a follow-up patch to fix the reporting job. Total downtime: 12 minutes.

13 Zero-Downtime Schema Changes (Expand/Contract)

Change the schema while millions of users are using the app.

What A 3-phase pattern for breaking schema changes.
Why Traditional "stop the app, change the schema, start it again" causes downtime.
How Expand → Migrate → Contract, deployed separately.

The problem

If you rename username to user_name in one migration and deploy the new app at the same time:

  • Old app instances still write to username — crash.
  • New app instances read from user_name — data is missing.
  • Rollback is a nightmare.

The pattern — 3 deployments

Phase 1 — EXPAND (additive changes only)

  • Add the new column user_name.
  • Old app keeps working — it doesn't know about the new column.
  • DB is now "backwards compatible."

Phase 2 — MIGRATE (dual-write / backfill)

  • Deploy app code that writes to both old and new columns.
  • Backfill existing rows: UPDATE users SET user_name = username.
  • Deploy code that reads from the new column, still writes to both.
  • Verify no writes are missing on either side.

Phase 3 — CONTRACT

  • Deploy app code that stops using the old column.
  • Wait a "safety window" — often days — in case rollback is needed.
  • Drop the old column.

A concrete example — renaming a column

-- V10: EXPAND
ALTER TABLE users ADD COLUMN user_name VARCHAR(100);

-- Deploy app v2 that writes both:
-- INSERT ... (username, user_name) VALUES (?, ?)

-- V11: BACKFILL
UPDATE users SET user_name = username WHERE user_name IS NULL;

-- Deploy app v3 that reads user_name only, still writes both.
-- Deploy app v4 that stops writing to username.

-- V12: CONTRACT (after days of confirmed stability)
ALTER TABLE users DROP COLUMN username;

Common expand/contract scenarios

ChangeHow to do it safely
Rename columnAdd new → dual-write → switch reads → drop old
Change column typeAdd new-typed column → migrate values → switch code → drop old
Split tableCreate new tables → dual-write → migrate → switch reads → drop old
Add NOT NULL columnAdd nullable → backfill → set NOT NULL
Real-World Use Case — Netflix, GitHub, banks Any service that can't afford downtime uses expand/contract. GitHub famously renamed the "master" branch column to "default_branch" using this pattern over several weeks, never taking the service offline.
Trade-off Zero-downtime = more deployments, more code complexity (dual-writes), more discipline. Only use for services where downtime is genuinely unacceptable.

14 Data Migration and ETL Considerations

Moving data — not just structure — from one place to another.

What Bulk-moving data from a source to a target, with transformations.
Why Old system retiring, warehouse loading, table splits, replatforms.
How ETL pipelines: Extract, Transform, Load.

What is ETL?

StepWhat it doesExample
ExtractRead data from source (DB, CSV, API, file)Dump 20M rows from legacy Oracle
TransformClean, reshape, enrich, deduplicateParse dates, split full name into first/last, drop test rows
LoadInsert into the targetBulk insert into PostgreSQL analytics DB

You may also see ELT — extract, load raw, then transform inside the warehouse (common with Snowflake / BigQuery).

Key considerations

  • Volume — 1000 rows fits in RAM. 1 billion rows needs streaming/batching.
  • Downtime tolerance — can the source be frozen during migration? If not, plan for change data capture (CDC).
  • Data quality — dirty data (NULLs, bad formats) causes migrations to fail halfway.
  • Idempotency — re-running the pipeline must produce the same result, not duplicates.
  • Referential integrity — load parents before children.
  • Progress tracking — log rows processed, failed, skipped.

Batching pattern

long lastId = 0;
final int batchSize = 5000;

while (true) {
    List<Row> batch = source.fetch(lastId, batchSize);
    if (batch.isEmpty()) break;

    List<Row> transformed = batch.stream().map(this::transform).toList();
    target.bulkInsert(transformed);

    lastId = batch.get(batch.size() - 1).getId();
    log("Migrated up to id " + lastId);
}

Common tools

  • Spring Batch — Java-native chunked processing with restart, retry.
  • Apache NiFi / Airflow — visual/DAG pipeline orchestration.
  • AWS DMS, Google DMS — cloud-managed DB migration.
  • Airbyte / Fivetran — pre-built connectors for hundreds of sources.
  • Debezium — change data capture (CDC) via DB logs.
Real-World Use Case — Retail moves to a data lake A retailer with 15 years of sales history in Oracle wants Snowflake for analytics. They set up Debezium to stream changes to Kafka, a Spark job transforms and loads into Snowflake. Historical backfill takes 3 days; the live stream keeps Snowflake in sync forever. Analysts get 100× faster reports.

15 Migrating Between Database Engines

Oracle → PostgreSQL, MySQL → Aurora, SQL Server → Postgres.

What Changing the DB vendor while keeping the same data.
Why Cost, licensing, cloud-native features, vendor lock-in.
How Convert schema, copy data, adapt SQL, cutover.

What can go wrong — the "surprise list"

CategoryExample difference
Data typesMySQL TINYINT(1) = Postgres BOOLEAN; Oracle NUMBER = many possible target types
Auto-incrementMySQL AUTO_INCREMENT vs Postgres SERIAL / IDENTITY vs Oracle sequences
PaginationMySQL/Postgres LIMIT/OFFSET vs Oracle ROWNUM / FETCH FIRST
Case sensitivityOracle: uppercase identifiers by default; Postgres: lowercase, case-sensitive if quoted
BooleansOracle has no native boolean type — usually stored as CHAR(1) or NUMBER(1)
String functionsCONCAT, SUBSTR, NVL vs COALESCE
Date/timeDifferent formats, time zones, functions (SYSDATE, NOW(), GETDATE())
Stored procs / triggersPL/SQL vs PL/pgSQL vs T-SQL — usually rewritten by hand
Character setsUTF-8 vs Latin1 vs UCS2 — data loss possible if mismatched
Isolation defaultsOracle default is stronger than MySQL's

A safe migration approach

  1. Assessment — inventory all stored procs, triggers, views, unusual SQL.
  2. Schema conversion — use a tool (AWS SCT, Ora2Pg) as a first pass, then hand-fix.
  3. Data copy — bulk load (COPY, LOAD DATA INFILE) is 10–100× faster than row-by-row.
  4. Application adaptation — swap dialect, JDBC driver, any raw SQL. If you're using JPA, most of this is free — just change the Hibernate dialect.
  5. Testing — run the full test suite against the new DB.
  6. Dual-write cutover (for zero downtime): write to both DBs, gradually switch reads, decommission old DB.

Why JPA helps enormously

Apps built on JPA / Hibernate often need only a config change to swap DBs:

spring.datasource.url=jdbc:postgresql://.../shop
spring.jpa.database-platform=org.hibernate.dialect.PostgreSQLDialect
# (was): org.hibernate.dialect.MySQLDialect
Real-World Use Case — Skipping Oracle license fees A mid-size company migrates from Oracle to PostgreSQL to save $2M/year in licensing. They use AWS DMS for a continuous data copy during a 2-month dual-run period. Their JPA-based app changed one config line; their 400+ stored procedures took 3 months to port to PL/pgSQL — the real work.

16 Validating Data Integrity Post-Migration

Answering the question: "Did we actually move everything correctly?"

What Systematic checks to prove source and target data match.
Why Silent data loss is the worst kind of bug — it's discovered months later.
How Counts, checksums, sampling, business-rule validation.

Layered validation strategy

  1. Row counts — quickest, catches missing tables/rows.
  2. Aggregates — sums of amounts, min/max of dates, distinct counts.
  3. Checksums / hashes — hash key columns per row and compare.
  4. Random sampling — pick 1000 random rows, compare byte-by-byte.
  5. Referential integrity — no orphan foreign keys.
  6. Business rules — every order has ≥ 1 item; every user has a valid email format.
  7. Application smoke tests — critical user journeys work end-to-end.

Sample validation SQL

-- Row counts
SELECT COUNT(*) FROM source.orders;
SELECT COUNT(*) FROM target.orders;

-- Financial totals — must match to the cent
SELECT SUM(amount) FROM source.transactions;
SELECT SUM(amount) FROM target.transactions;

-- No orphaned foreign keys
SELECT COUNT(*) FROM target.orders o
LEFT JOIN target.users u ON o.user_id = u.id
WHERE u.id IS NULL;

-- Checksums (Postgres example)
SELECT MD5(STRING_AGG(id::text || email, ',' ORDER BY id))
FROM users;

Automated validation tools

  • AWS DMS validation — built-in row-by-row compare.
  • Great Expectations — declarative data-quality checks (row counts, ranges, uniqueness).
  • dbt tests — add not_null, unique, relationships tests in YAML.
  • Custom scripts — Python/Java jobs comparing hashes.

Best practices

  • Keep the old DB read-only for a rollback window (days to weeks).
  • Run validation both immediately after migration and after the first business day.
  • Involve the business team — they know which totals must never change.
  • Document every discrepancy found, even if small.
Real-World Use Case — Bank ledger migration A bank moves 500M ledger rows to a new system. Validation includes: (1) row count per branch, (2) sum of all debits = sum of all credits (must be exactly zero), (3) daily closing balance per account matches source to the paisa. They keep the old system in read-only mode for 6 months. Two subtle rounding bugs are caught in month 2 and patched with fix-forward migrations.
Success criteria Migration is only "done" when: counts match, sums match, checksums match, foreign keys are clean, and the app has run cleanly in production for one full business cycle.
